## 公众号版（深度 · 1500-2000 字）

标题：**每天自动巡检的脚本说「0 条问题」，你信吗？**

你有没有过这种时刻？

凌晨跑完的全量校验，天亮了你端起咖啡，点开结果页。

**「失败原因：0 条」**

第一反应是什么？松一口气。今晚不用加班了。

**先别睡。**

这不是好消息——这很可能是一条**假绿**。

### 一、88 个文件，枚举器说 0 个

说个昨天发生在我自己仓库里的事。

那天我照例跑全量体检：88 个 case，一个一个校验，输出全部落盘。然后我写脚本解析这些输出，把失败原因分桶统计。

脚本跑完了。

**0 条失败原因。**

干净、漂亮、一行警告都没有。

但我手边另一份独立记录写着：**88 个 case**。

我回头去数那个输出目录——**88 个文件躺在那儿**。

枚举器说 0 个，目录里有 88 个。

**差 88。就是全部。**

### 二、真凶：一个点号

那 88 个输出文件，我是这么命名的：

```
把 "./做事技巧/H5设计转H5滑动" 这种路径里的斜杠换成下划线
→ "._做事技巧_H5设计转H5滑动.txt"
```

问题就出在最前面那个点。

**Python 的 `glob.glob('*.txt')`，按 POSIX 语义，`*` 不匹配以点开头的名字。**

所以 88 个文件被整体跳过，枚举器返回了一个**空列表**。

它没有报错。没有警告。退出码是 0。日志干干净净。

它不像是坏了，它像是**本来就没东西**。

### 三、为什么「0 条问题」比「53 条失败」更危险

报错的系统是安全的——它会把你拽过去。

**假绿不是。**

「53 条失败」会让你皱眉、会去查、会发现工具坏了。

「0 条失败」只会让你**合上电脑，去睡觉**。

而且零结果有个特殊性质：**它不需要解释**。

没有任何脚本会对「我没找到问题」发出警告。你的直觉会说「没报错就是没问题」——但「没报错」和「我真能找到问题」是**两件完全不同的事**。

更糟的是这条假结论**差点就写进历史记录**。

如果我当时没多看一眼那个 88，我的巡检日志里就会多一行：「本轮 0 条失败原因，仓库状态良好。」

**一条错误结论，混进一串正确结论里，比一次崩溃难查一百倍。**

### 四、统计有两个漏点，上一轮我只堵了一个

这轮踩坑让我回头看了上一轮（11-26）的沉淀。

上一轮我修的坑是：跑校验时用 `| tail -5` 截断输出，导致失败详情行全被掐掉，而**退出码分布完全正确**——分类计数全错，但没人收到任何信号。

那轮的结论是「全量落盘，别在管道上统计」。本轮我照做了。

**结果本轮又踩了。**

因为**统计有两个彼此独立的丢失通道**：

1. **产生端**：`| tail -5` / `| head` / `grep -m` 在**数据流上**截断 → 上一轮修好了
2. **枚举端**：`glob` / `ls` / shell 通配在**收集文件时**就漏 → 本轮踩的

上一轮的修法解决的是「行会不会丢」，**根本没碰「文件会不会少」**。

风险只是从一层挪到了另一层。

**这就是这类 bug 最真实的形状：修好一个通道，会给你「已经安全了」的错觉。**

所以通用判据是这句——

> 任何要用来做统计的集合，都必须能说清楚：**我是怎么枚举出来的。**

### 五、三件套：先对收据，再看内容

鉴别丢件，其实只需要一个动作：**把两个数摆在一起比。**

**Step 1 · 先造期望数**

在跑统计**之前**，就写下一个**独立来源**的期望数量。比如「上轮记录了 88 个 manifest」。

关键是「独立来源」。**不能拿同一个 glob 的结果当期望数**——那是同一把尺子量自己，永远相等，等于没量。

**Step 2 · 同时记实际数**

统计跑完立刻打印：**我实际枚举到多少个样本**。

注意是「我数到几个样本」，不是「统计结果里有几条」。这两个数经常不是一回事。

**Step 3 · 对账再解读**

两个数不等 → **先怀疑枚举器，再怀疑内容**。

两个数相等 → 才轮得到看统计结果本身。

顺序不能反。反了就是拿着一个可能瞎了的统计器去评判内容。

### 六、诊断时只加对照，不改原路

有一个反模式，我差点踩：

「我把 glob 改成 listdir 试试看？」

**别。**

一旦你改了原命令，就永远不知道**原本漏了多少**。你会带着一个「现在看起来对」的结果继续往下走，而真正的缺口被你亲手抹掉了。

正确做法是：**另加一路对照**。

同一个目录，用**两种枚举器**各数一遍（`glob` vs `os.listdir`，或 `find` vs `ls`），**两数不等 = 有丢件**。

原路不动，对照另起。

还有一个配套细节：临时产物放系统临时目录，**别写进被统计的目录**——否则你给自己造了一次新的口径漂移。

### 七、想宣布「这轮没问题」，得拿出四个证

| 证 | 内容 | 管什么 |
|---|---|---|
| 证一 · 期望数 | 期望统计到的样本数，来自**独立来源** | 样本完整性 |
| 证二 · 实际数 | 实际枚举到的样本数，来自**至少两个枚举器** | 样本完整性 |
| 证三 · 失败数非零 | 真的跑出了失败详情行 | 计算正确性 |
| 证四 · 逐桶对齐 | 分类计数与上一轮**逐桶相同** → 零回归 | 计算正确性 |

前两个证管「**有没有少**」，后两个证管「**算得对不对**」。

四个齐了才能说「这轮没问题」；缺任何一个，最多只能说「没发现异常」。

再补一条最实用的底线——

> **「结果是 0」在拿到证一之前，只能读作「统计工具瞎了」。**

### 收束

把整套动作压成五步，每天巡检照着跑：

1. **先记期望数**（独立来源，写下来，别等跑完再想）
2. **全量落盘**（输出不经会丢行的管道）
3. **双路枚举**（两种枚举器各数一遍）
4. **对账**（期望 vs 实际，不等就先查枚举器）
5. **逐桶对齐 + 留档**（把口径写进记录，让下一轮有尺子可对）

底下那句话，是我今天最想留给自己的：

> **先记账数，再看内容。**
>
> 而当账本是空的，先怀疑尺子，别急着庆祝。

## AI 阅读版（结构化 · 供模型直接取用）

### 一句话

统计结果少东西时，先证明**枚举器是好的**，再相信那个 0。

### 适用场景

- 每日/每小时自动巡检、只报数字的巡检系统
- 批量校验脚本的失败原因分桶统计
- CI 巡检看板、每日数据对账、备份完整性校验
- 任何"扫一批文件、统计一批指标"的自动化

### 症状（三个面孔）

| 面孔 | 表现 | 危险度 |
|---|---|---|
| 计数归零 | 失败详情一条都解析不出来，bucket 全空 | 最高（看起来是全绿） |
| 数量对不上 | 期望 88 个，实际枚举到 0 个或 40 个 | 高 |
| 样本不完整 | 总数正常，但掺了不该有的样本（隐藏文件/临时文件） | 中 |

共性：**不抛异常，退出码 0，日志干净。**

### 根因（两个独立丢失通道）

| 通道 | 丢失发生在 | 典型触发 | 修法 |
|---|---|---|---|
| 产生端 | 数据流上 | `\| tail -5`、`\| head`、`grep -m`、`sort \| head` | 全量落盘 `> out.txt 2>&1`，在文件上分类 |
| 枚举端 | 收集文件时 | `glob.glob('*.txt')` 不匹配前导点；`ls`/`find` 同样 | 双路枚举 + 对账 |

**关键**：修掉一个通道不代表另一个安全。修好一个通道会产生「已经安全了」的错觉。

### 方法论三件套（顺序不可换）

1. **先造期望数** —— 在跑统计之前，从**独立来源**写下"我期望统计到多少个"。不能拿同一个 glob 的结果当期望数（同一把尺子量自己）。
2. **同时记实际数** —— 统计跑完立刻打印"我实际枚举到多少个**样本**"（不是"统计结果里有几条"）。
3. **对账再解读** —— 不等 → 先怀疑枚举器，再怀疑内容；相等 → 才看统计结果本身。

### 反模式（诊断时别做的三件事）

- ❌ 改原枚举命令去"试试看"——改了就永远不知道原本漏了多少
- ❌ 拿同一个 glob 的结果当期望数——同一把尺子量自己
- ❌ 把临时产物写进被统计目录——给自己造新的口径漂移

### 正确替代

- ✅ **另加一路对照**：同目录两种枚举器各数一遍（`glob` vs `os.listdir` / `find` vs `ls`），两数不等 = 丢件
- ✅ 临时产物放系统临时目录
- ✅ 鉴别阶段只读，不改不删不恢复

### 验收标准（四个证同时成立）

| 证 | 内容 | 职责 |
|---|---|---|
| 证一 · 期望数 | 来自独立来源（上轮记录 / 上游清单） | 样本完整性 |
| 证二 · 实际数 | 来自至少两个枚举器 | 样本完整性 |
| 证三 · 失败数非零 | 真的跑出了失败详情行 | 计算正确性 |
| 证四 · 逐桶对齐 | 分类计数与上一轮逐桶相同 → 零回归 | 计算正确性 |

**四个齐了才能说"这轮没问题"；缺任何一个，最多只能说"没发现异常"。**

### 五步落地卡

1. 先记期望数（独立来源，写下来）
2. 全量落盘（不经会丢行的管道）
3. 双路枚举（两种枚举器各数一遍）
4. 对账（期望 vs 实际，不等就先查枚举器）
5. 逐桶对齐 + 留档（把口径写进记录，让下一轮有尺子可对）

### 底线

> **「结果是 0」在拿到证一之前，只能读作「统计工具瞎了」。**

### 实战锚点

- **场景**：pretty-skill 仓库全量 check-3f 巡检，88 个 manifest
- **丢件数**：88 → 0（全丢）
- **触发**：`glob.glob('*.txt')` 不匹配 `._` 前导点文件名
- **退出码**：0（无警告）
- **差点写进历史的假结论**：「本轮 0 条失败原因」
- **抓它的不是复查，是另一份独立记录里的 88**
- **一句话**：先记账数，再看内容；账本是空的，先怀疑尺子
