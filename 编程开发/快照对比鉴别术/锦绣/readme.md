## 公众号版（深度 · 1500-2000 字）

标题：**每天早上的第一眼：巡检数字掉了，先别急着找备份**

你有没有过这种时刻？

凌晨跑完的自动巡检，早上你揉着眼扫一眼屏幕——**数字红了一格**。

那一刻你的大脑会自动完成一次判断：**出事了**。

然后你开始找备份、找恢复、找历史版本、翻文件、比对时间戳……一整套动作行云流水，做完才发现——**东西一个都没少**。

我不是编的。这事在我自己的仓库上刚发生了一次。

### 一、掉的是 3 个，差的是 9.4 MB

先摆现场。

我维护一个内容仓库，每天凌晨跑一次全量体检：把每个 case 逐个校验一遍，出一张"87 个 case，34 个通过、53 个不通过"的成绩单。跑完记一笔日志，第二天照着昨天的数字对一下。

那天早上，两个数字对不上：

| 项目 | 昨天记录 | 今天实测 | 差 |
|---|---|---|---|
| PDF 文件数 | 40 | 37 | **-3** |
| PDF 总字节 | 123,863,174 | 114,411,595 | **-9,451,579** |

**少了 3 个文件，少了 9.4 MB。**

按理说，这该触发一条"文件疑似丢失"的告警。

但我盯着这两个数看了十几秒，脑子里冒出来的第一个念头不是"谁删了我的文件"，而是——

**等一下，昨天那 40 个，是怎么数出来的？**

### 二、真相：桌子没动，换了把尺子

翻回昨天的日志，昨天记的是 `find . -name "*.pdf"`。

今天我查的是 `find . -name "*讲解.pdf"`。

**一字之差，口径就变了。**

这个仓库里有 3 个历史遗留的 PDF 变体（`-v2` / `-v3` / `-v4`，同一份内容改了三版的存档），它们**不叫"讲解.pdf"**，所以今天的统计口径把它们全漏掉了。

3 个。**一个不少，正好是差额。**

而真正的硬证据是这条：

> 全量 `*.pdf` 字节总量 = **123,863,174**
> 昨天记录的字节总量 = **123,863,174**
> **差 0 字节。**

**一个字节都没少。**

所以真相是：东西没丢，**是昨天用了宽口径，今天用了窄口径**。

如果我没多问那一句"昨天怎么数的"，接下来会发生什么？——我会开始找备份、比对 inode、检查回收站、甚至考虑从 Git 历史里恢复。**动的是数据，浪费的是一整晚。**

### 三、为什么人会在这里翻车

因为巡检系统有一个隐含设计前提：**"输出不变"本身就是一个信号**。

输出没变 = 系统没动 = 安全。
输出变了 = 有什么变了 = 出事了。

这条设计本身是对的，它能抓住真正的故障。但它有一个**致命的盲区**：它把"**东西变了**"和"**你看东西的方式变了**"混成了同一件事。

而这两种情况的正确处理是完全相反的：

- 东西真变了 → 要**恢复**
- 尺子变了 → 要**对齐口径**

搞反了，代价不是"判断错了"，是**你在健康的数据上执行恢复操作**。

### 四、更阴险的第二层：被掐掉尾巴的日志

我一开始是怎么统计的？

```bash
python3 check-3f.py "$dir" 2>&1 | tail -5
```

每个 case 只看最后 5 行。跑了 87 个 case，看着挺整齐。

然后我要统计"失败原因分几类"——这时候才发现不对了。

因为 ❌ 的详情行（"缺讲解.pdf"、"缺 images/ 目录"、"页数不一致"）**全在中间，被 `tail -5` 掐掉了**。最后 5 行只剩下一句"有检查项失败 · PR 会被自动退回"。

**最恶心的地方在这儿**：退出码是对的。

`EXIT=0` 34 个、`EXIT=1` 53 个——**分毫不差**。你从退出码上看，一切正常。

但 9 类失败原因的分类计数，是**全错的**。

这就是这个坑最贵的地方：它不是报错，是**静默地算错**。你不会收到任何信号，只会拿到一个偏低的 bucket 数，然后拿着它去下判断。

修法就一行：

```bash
python3 check-3f.py "$dir" > out.txt 2>&1   # 全量落盘
# 然后在"文件"上分类，不要在"管道"上分类
```

**通用判据：任何要用来做统计的输出，都不能经过会丢行的管道。** `tail`、`head`、`grep -m`、`sort | head` 全是隐形截断器。管道是给人看的，文件才是给统计用的。

### 五、三件套：对口径、比字节、查分类

这次之后，我把这套动作压成了三步。

**第一步 · 对齐口径。**
把两轮的匹配 pattern、时间窗、归一化规则**写成同一行**并排放着，再开始比。口径三要素必须**三同时同**：pattern、时间窗（含边界）、归一化（大小写 / 路径前缀 / 排序）。最容易漂的是 pattern——你写命令时随手从 `*.pdf` 改成 `*讲解.pdf`，**自己完全不记得**。

**第二步 · 用字节总量判生死。**
文件数会骗人：改名、替换、拆分，都能让文件数对不上。但**总字节逐字节相等，几乎不可能是巧合**。这是"零丢失"最硬的单一证据——比"我看了目录，文件都在"强得多，因为它不依赖你的记忆和注意力。

**第三步 · 全量捕获再分类。**
输出落盘，按**真实的 ❌ 行**解析出各类失败原因，**不要 grep 猜数**。然后逐桶跟上一轮对齐——桶数不变，就说明没有回归。

三步**顺序不能换**。口径不对齐，后面全是噪声；生死没判清，分类就是在错误前提下的精细活。

### 六、三个数齐了才能下结论

最后我给自己定了三个验收数：

| 数 | 这次的值 | 排除了什么 |
|---|---|---|
| **口径对齐** | pattern / 时间窗 / 归一化 逐条写下来 | 排除"换尺子" |
| **字节总量** | 123,863,174 = 123,863,174（差 0） | 排除"真丢" |
| **bucket 分布** | 50/49/47/34/5/2/1/1/1，逐桶不变 | 排除"坏了" |

**三个数齐了，才能说"仓库状态正常"。缺任何一个，最多只能说"没发现异常"。**

这三个数的分工很清楚：数一排除"你看错了"，数二排除"东西没了"，数三排除"东西坏了"。

### 七、还有一步：把口径留档

这次修完，我把**本轮用的口径**也写进了日志。

听起来是废话，但它是整个循环里最容易被省掉、也最致命的一步——**今天不记，明天早上你手上又只剩一个数字，没有那把尺子**。

所以最后是五步：

1. **对齐口径**：上轮 pattern + 时间窗 + 归一化，并排抄下来
2. **读全量**：校验输出全量落盘，不要在管道上统计
3. **判生死**：最宽 pattern 重算，比**总字节**（不是文件数）
4. **查分类**：按真实 ❌ 行解析 bucket，逐桶与上轮对齐
5. **留口径**：把本轮口径写进记录，让下一轮有尺子可对

底线一句：**没对齐口径之前，不要断言"东西丢了"，更不要动手恢复。**

鉴别阶段只读，修复阶段才动刀。
