## 公众号版（深度 · 1500-2000 字）

标题：**每轮对话的开头，都有一笔跟你今天说什么无关的固定开销**

你有没有发现，Agent 跑得越久，你越觉得「怎么这么费 token」？

一开始你以为是自己提示词写长了、上下文堆多了。后来把账单拆开才发现——**最大的一笔压根不在你的对话里**。

它在你对话**开始之前**。

每一轮，运行时都会往系统提示里塞两样东西：**一份技能目录**（这个 Agent 此刻能调用哪些工具）和**一份记忆全文**（它自己的长期笔记）。这两样东西跟你今天问什么**完全无关**，但每一轮都要付一遍。

我实测过自己这套运行时：优化前**每轮固定注入 29,152 tokens**。其中技能目录 **356 条**，记忆全文 **83,309 字节**。

最扎眼的是这个数字：**356 条技能描述里，348 条被截断到短于 20 个字符**。

换句话说，348 条技能在每轮对话里，模型看到的**几乎等于没有描述**。有效描述占比只有 **2%**。

你一边在抱怨 token 贵，一边每轮都在读一份「几乎全是噪音」的清单——浪费的不只是钱，还有注意力。上百个半截描述叠在一起，工具选择能不模糊吗？

### 一、先别急着删：你可能踩了两个假开关

这件事最耗时间的部分，不是删，是**找对开关**。

我一开始是照着源码里的 `loadSkills` + ignore 包逻辑，写了 `.ignore` 规则。源码就在那儿，看着完全对。

**结果：开/关两次真实会话，catalog 完全相同——360 条 / 17,364 字节，一模一样，连字节数都没动。**

原因是那套 ignore 逻辑属于 **Pi 兼容层**，而 MCode 走的是 `externalSkillRoot` **另一条路径**，**对外部技能根不读 ignore 文件**。

第二个坑是 `disable-model-invocation: true`。文档表格里白纸黑字写着「skill is hidden from system prompt」。我信了。

**它也不生效。** MCode 的 frontmatter 解析器**不读这个字段**，加了照样出现在目录里。

两个开关，两个都是「文档说能用、运行时就是不读」。

**教训：文档 ≠ 实现，兼容层 ≠ 执行路径。** 读代码时得分清哪段是给你走的，哪段是留给别的兼容层的。真要省时间，就先花 10 分钟找到**运行时真正读的那一行**，再动手。

### 二、真正管用的，只有一个字段

在运行时过滤链上翻了两圈，找到了它：

`filterInjectableRegistrySkills` → `.filter((entry) => entry.frontmatter.listed !== false)`

**唯一被真正读取的字段是 `listed: false`。**

加一行，这个技能就从每轮注入的目录里消失了。

注意这里的关键词：**隐藏 ≠ 卸载**。它只是不再每轮报到，需要的时候照样 `skill({name})` 按名加载。

别急着批量。先做**单点验证**：

1. 拿**一个**技能加 `listed: false`
2. 起一个**真实新会话**
3. 读它的 `systemPrompt`
4. 确认这一条消失了，**同时对照组还在**

我实测的就是这样：`hta-agent-architecture-auditor-agent` 加了就从目录消失，`agent-reach` 作为对照项**依然在**。这一步很重要——它证明你是「精准关掉这一条」，不是「整个目录崩了」。

还有一个坑：**`~/.agents/skills` 里多数条目是软链**，指向 `~/dsh-skills` 或 `~/.claude/skills`。改软链会改到实体。动手前先 `readlink` / `realpath` 找到真实文件。

### 三、剪完之后，文件变大了——这不是失败

这是我踩过最反直觉的一刀。

优化完的效果：条目 **356 → 249（少 107 条）**，但 catalog 块的字节数 **17,364 → 19,220**。

**涨了 1,856 字节。**

第一反应是：我是不是白干了？

后来找到原因：catalog 有个 **5,000 token 的硬预算**（`min(contextWindow × 2%, 5000)`，**不可配**）。装不下就先截断描述，再装不下就整个省略条目。

所以剪掉 107 个条目腾出的预算，让**原本被截断到只剩几个字符的描述显示完整了**。

有效描述占比：**2% → 99%**（短于 20 字符的条目 348 → 2）。

**所以判断成败，看条目数和有效描述占比，不要看字节数。** 拿字节数当指标，你会得出「优化让文件变大了」这种荒谬结论。

顺便说一句：别想通过调 `contextWindow` 来省。2% × 512,000 = 10,240 > 5,000，早就顶到硬上限了，**改 context 一分钱都省不到**。

真正省下大头的其实是记忆瘦身：常驻只留「跨任务都可能触发的热规则」，专项实战迁到 topic 文件**按需加载**——**83,309 B → 11,270 B（-86%）**。

### 四、零破坏：这才是敢动手的前提

我做这次改造时给自己定的规矩是：**每一处改动都必须可逆**。

- **只加一行。** 215 个技能**只加 frontmatter 一行**，正文一个字没删，仍可按名加载。
- **逐字节对账。** 记忆迁移必须**46/46 条正文逐字节命中**（83,057 B → 83,057 B，**差 0**）。差 1 字节都要查清——「差 0」是唯一能签字的数字。
- **合规池零误伤。** 我要砍的目录里有 19 个 knowhub 技能，那是你的合规技能池，不能砍。做法是**先迁到原生 user 根**（`~/.minimax/skills/`）再关外部根——**先确认它们有替代来源，再动手**。
- **三个备份先落盘。** frontmatter 原文件、记忆原文、软链拓扑清单，改之前全部存好。
- **写好回滚脚本，并且实测跑一次。** 不实测的回滚脚本等于没有回滚脚本。

还有一条容易忽略：**改动在下一个会话生效**。不要在同一轮里既改又验——你验的是旧状态。

### 五、怎么才算验过：只认真实会话

这是整件事里最值钱的一条方法论。

**模拟器会骗你。** 权威验证只有一条路：起一个**真实新会话** → 取它的 `llm-call.json` → 读 `systemPrompt` 字段 → 正则提 `<available_skills>` 块 → 数条目。

解析的时候还有个坑：条目名要用 `^- ([^\s]+): ` 提取。用 `[^:]+` 会把 `lark:lark-approval` 这类**带前缀的名字截断**，计数直接虚高。

要同时量**三个数**，不是一个：条目总数 / 描述短于 20 字符的条目数 / 记忆文件字节。单看任何一个都会得出片面结论。

最终账单（真实会话实测，不是估算）：

| 项目 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 技能目录条目 | 356 | 249 | **-107** |
| 描述短于 20 字符 | 348 | 2 | **-346** |
| 有效描述占比 | 2% | **99%** | +97pp |
| MEMORY.md | 83,309 B | 11,270 B | **-86%** |
| **每轮固定注入** | 29,152 tok | **8,039 tok** | **省 21,113（-72.4%）** |

**100 轮会话省 211 万 tokens，1000 轮省 2,110 万。**

### 六、五步落地卡

1. **量**：真实新会话读 `systemPrompt`，数条目 / 数截断描述 / 量记忆字节，记基线。
2. **定位**：在运行时过滤链上找**真正被读取的那一行**（本例 `frontmatter.listed !== false`）。别信文档，别信兼容层。
3. **单点验证**：1 个实验 + 1 个对照项，真实新会话确认「只消失一条」。
4. **批量 + 备份**：先备份再改；记忆逐字节对账差 0；合规池先迁原生根。
5. **复验 + 回滚**：真实新会话复测三个数 → 写并实测 `ROLLBACK.sh` → 下个会话才生效。

三个验收标准：**条目数降了** ✅ · **有效描述占比升了** ✅ · **记忆字节降了** ✅。
字节数**不要求降**。

底线一句：**别拿模拟器当验收**——它跟你要治理的运行时，根本不是同一套代码。

**先量出每轮固定注入，再决定砍谁。**
