## P0 · 封面 / 定位

- **标题**：接口可信度鉴别术
- **章节类型**：封面 / 定位
- **核心主张**：「请求返回 200」是最容易骗人的信号——你验的是**传输层**，用户信的是**内容层**
- **认知锚点**：「一个永远亮绿灯的仪表盘」——表针稳稳指在绿区，机器却根本没在转
- **关键要点**：
  - 状态码只能证明**字节到了**，不能证明**字节对**；而接口的限流恰恰发生在内容层
  - 坏数据有三张统一的面孔：伪装成一条正常快讯、伪装成一页 MySQL 报错、伪装成"最新"的一条旧数据
  - 鉴别要放在**语义层**：给数据加"不可能值"哨兵，让它自己喊"我不对劲"
  - 一句话口径：**你验的是传输层，用户信的是内容层**
- **数据 / 数字**：3 张伪装面孔 · 1 层语义校验 · 0 次重试
- **金句**：请求成功是最容易骗人的信号

## P1 · 现象 / 痛点

- **标题**：假数据的三张面孔
- **章节类型**：现象 / 痛点
- **核心主张**：坏数据不会以"报错"的样子出现——它会**穿着正常条目的衣服**混进你的结果里
- **认知锚点**：「三条戴着同款面具的快讯」——三张一模一样的稿纸，其中一张写的是"访问受限"
- **关键要点**：
  - 面孔一 · **限流提示伪装成一条快讯**：HTTP 200 + 合法 JSON，内容是「此IP访问受限制，请360分钟后再重新尝试」，字段一个不缺——但它的 `Level` 是 `"0"`，在这个源里 **`0` = 重磅 = 最高优先级** → 不识破就直接把限流提示当头条推给用户
  - 面孔二 · **报错页伪装成 JSON**：漏传分页参数时，后端把 MySQL 原始报错当正文返回（`Query failed: You have an error in your SQL syntax`），HTTP 照样 200
  - 面孔三 · **旧数据伪装成"最新"**：假条目的时间戳是 `2020-01-01 00:00:00`，在"按时间倒序取最新"的逻辑里会被排到**末尾**，看起来就像一条正常的历史条目
- **数据 / 数字**：3 张面孔 · 1 个假 `Level=0` · 360 分钟封禁 · 2020-01-01 哨兵值
- **金句**：越像一条正经快讯的假数据，越难被发现

## P2 · 根因 / 原理

- **标题**：为什么"检查状态码"这个习惯必然漏
- **章节类型**：根因 / 原理
- **核心主张**：状态码校验验的是"有没有传回来"，内容层被整个绕开——而限流**只发生在内容层**
- **认知锚点**：「一扇只装了门锁的保险柜」——锁是好的、密码是对的，门却装着
- **关键要点**：
  - 原理一 · **校验层错位**：HTTP 200 证明字节到了，不证明字节对；schema 校验通过也不证明语义对
  - 原理二 · **限流提示复用业务结构**：服务端把错误信息包进正常条目的字段里，客户端的 schema 校验 **100% 通过**——这是"看起来完美"的失败
  - 原理三 · **排序把异常藏起来**：假条目带的是过去时间戳，倒序排到末尾；你的校验若只看"第一条"，反而永远看不到它
  - 原理四 · **静默流进下游 = 把错误当数据用**，比直接报错更坏——错数据会被当事实继续加工，越走越远
  - 补一条同源陷阱：响应头三个字节是 **UTF-8 BOM**，`JSON.parse()` 直接抛 `Unexpected UTF-8 BOM`——不是内容问题，是**协议层的脏字节**
- **数据 / 数字**：4 条成因 · schema 100% 通过 · 1 个 BOM 陷阱 · 0 处报错
- **金句**：格式合法的东西，最擅长伪装成内容正确

## P3 · 诊断 / 排除

- **标题**：语义哨兵校验——给数据加一道"不可能值"检测
- **章节类型**：诊断 / 排除
- **核心主张**：状态码之后再加一道**语义特征校验**，命中哨兵值即判定为异常响应，**显式报错，绝不让它静默流进下游**
- **认知锚点**：「三个会自己报警的哨兵」——三个站在数据通道入口的小哨兵，坏数据一过来就吹哨
- **关键要点**：
  - 哨兵一 · **时间戳不可能区间**：最新一条的时间早于进程启动时间，或落在 `2020-01-01` 这类明显不可能的区间 → 判定异常
  - 哨兵二 · **正文命中限流词**：「访问受限制 / 请稍后 / 系统维护 / 频繁访问」→ 判定异常（这一条最直接，成本最低）
  - 哨兵三 · **关键字段突然全为默认值**：等级、时间、来源等字段集体塌成同一个默认值 → 判定异常
  - 落地要求：异常响应要**能被单独识别并显式报错**；命中即拦下，不能让它流到下游
  - 反面判据：**"没有报错"不等于"数据对"**——静默流进下游比直接报错更危险
- **数据 / 数字**：3 类哨兵 · 1 个不可能区间 · 0 次静默通过
- **金句**：让数据自己喊"我不对劲"

## P4 · 处置 / 铁律

- **标题**：撞上封禁怎么办——四条铁律
- **章节类型**：处置 / 铁律
- **核心主张**：限流后**重试只会延长封禁**；正确做法是降级、显式标注时效，把等待时间交给用户决定
- **认知锚点**：「一扇六小时才重新开的门」——门上贴着倒计时，门外的人正在徒劳地敲
- **关键要点**：
  - 铁律一 · **不重试**：封禁时长就写在返回文本里（实测 **360 分钟**），重试等于加刑；且这类源**翻页会加重限流**（连续翻 **15 页**即触发封禁）→ 默认只拉 1 页，翻页之间加节流延迟
  - 铁律二 · **降级读缓存**：接口不可用时读本地快照，**在输出顶部标注「缓存数据，拉取于 X，N 小时前」**
  - 铁律三 · **把剩余等待时间告诉用户**，让用户决定"等"还是"先看缓存"，而不是替他猜
  - 铁律四 · **降级不推进消费水位**：拿缓存冒充实时，会把"其实没读到"的条目误标为已消费
  - 附带一条环境坑：本机 `http_proxy` 常指向**已失效的端口**（实测 `127.0.0.1:7892` 已死，实际在听的是 `7890`）→ 判据永远是 `lsof -iTCP -sTCP:LISTEN` 看谁在听，别按"我记得是哪个"
- **数据 / 数字**：360 分钟封禁 · 15 页触发 · 4 条铁律 · 1 个死代理端口
- **金句**：重试不是坚持，是加刑

## P5 · 根因 / 原理

- **标题**：增量消费去重——两种直觉写法都会错
- **章节类型**：根因 / 原理
- **核心主张**：单一水位线只能二选一——要么重复消费，要么漏读；两种直觉写法都跳不出这个框
- **认知锚点**：「一排只能盖一个章的记号笔」——盖满一整排纸，章却只能落在同一个位置
- **关键要点**：
  - 直觉一 · 用"上次输出**最后一条**"的时间当水位 → 接口是**倒序**返回的，最后一条其实是最旧的 → 已消费过的条目被反复吐出来（实测第二次跑仍返回一模一样的 3 条）
  - 直觉二 · 改用"上次输出**第一条**"的时间当水位（想修正上面那个）→ 被 `--level` / `--keyword` 过滤掉的**同批**条目永远读不到（它们的时间戳落在水位之前）
  - 正解 · 存**已消费条目的标识集合**（这里是时间戳集合），拉取时按集合做**差集** → 重复和漏读两个问题同时消失
  - 配套两条：① 只把"**实际输出过**"的条目记为已消费，被过滤掉的条目下次仍读得到；② 集合设上限（如 500 条）并按时间序裁剪，否则无限增长
- **数据 / 数字**：2 种直觉都错 · 1 个集合解法 · 500 条上限 · 3 条重复吐回
- **金句**：水位线只能记住一个点，增量需要记住一个集合

## P6 · 证据 / 量化

- **标题**：把接口封成 skill，值多少——3 轮 A/B 实测
- **章节类型**：证据 / 量化
- **核心主张**：封装的收益不是"信息更多"，是"**更快 + 更少踩坑 + 边界显式**"——这三样都能用数说
- **认知锚点**：「两条通向同一屋子的路」——一条绕山一圈，一条直着进门
- **关键要点**：
  - R1「最新重磅快讯」：裸做 **122.9s**（含从 DNS 污染到从内联 JS 反解出接口）→ 用 skill **98.5s**，**-20%**
  - R2「某股最近消息」：裸做 **594.1s**（569 条快讯翻 38 页 + 30 条公告 + 6 份公告全文 + 财务 + 行情）→ 用 skill **85.6s**，**-86%**
  - R3「过去半年」：裸做 **220.4s**（3 个源 19 次请求）→ 用 skill **142.8s**（4 页 60 条），**-35%**
  - 合计 **937.4s → 326.9s = -65%**（**2.87 倍**）；最痛的一次是 R2——省下的正是"把接口当谜题破"的那 10 分钟
  - **诚实边界（必须一起说）**：R2/R3 裸做拿到的**更多**（公告原文、财务、行情）→ skill 的价值是更快 + 更少踩坑 + **显式声明数据边界**，**不是覆盖更全**；拿一条快讯流冒充全面尽调，比明说边界更糟
- **数据 / 数字**：3 轮 A/B · 合计 -65% · 2.87 倍 · 937s → 327s
- **金句**：封装省下的不是数据，是把接口当谜题破的那 10 分钟

## P7 · 收束 / 速查

- **标题**：数据到手，三问才算合格
- **章节类型**：收束 / 速查
- **核心主张**：拿到数据后必须能回答三个问题——**数据是真的吗 / 覆盖了哪段时间 / 边界在哪**
- **认知锚点**：「一张三问通关卡」——三个必须打勾的框，少一个都过不去
- **关键要点**：
  - 自检一 · **真假**：哨兵校验过了吗（时间戳不可能区间 / 限流词 / 关键字段默认值）——没过就不要往下走
  - 自检二 · **时效**：最新一条距今多久？这次取数**覆盖了哪一段时间**？（实测该源"最新一条"通常滞后 **30–60 分钟**，采样间隔中位 **1.4 分钟**——不要自己编一个"刚刚更新"）
  - 自检三 · **边界**：这个源**不**覆盖什么？（实测 `Url` 字段 **100 条全空** → 没有原文出处链接；公告原文 / 财报 / 行情 / 研报都不在快讯流里，需另找源核对）
  - 交付形态固定三块：**结论先行**（直接回答）→ **条目列表**（时间 + 等级 + 标题 + 关联个股）→ **数据时效与边界**
  - 一条底线：降级到缓存时**必须显式声明数据已过时**，不能让用户以为拿到了实时数据
- **数据 / 数字**：3 问 · 3 块输出 · 1 条底线 · 滞后 30–60 分钟
- **金句**：说清楚边界，比多拿十条数据更值钱
