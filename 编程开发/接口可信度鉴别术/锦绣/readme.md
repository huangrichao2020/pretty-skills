## 公众号版（深度 · 1500-2000 字）

标题：**接口返回 200，JSON 也能解析——我差点把一条限流提示当成头条推给了用户**

写接口的时候，最容易让人上瘾的一句话是「请求成功了」。

状态码 200，JSON 也能正常解析，字段一个不缺，程序不报错，日志干干净净。你会顺手把它当成「数据没问题」——然后直接推给用户。

但有一个场景，会让这个习惯彻底失效：**接口限流**。

真实案例：做财经快讯的 skill，接的是快兰斯接口。一次取数，HTTP 200，JSON 完全合法，结构跟平时一模一样。看起来毫无问题。

然后我把返回体打开，注意到一条「快讯」的内容是这么写的：

> 此IP访问受限制，请360分钟后再重新尝试

这行字，被服务端原样包进了一条正常快讯的字段里。而它的 `Level` 字段是 `"0"`——在这个数据源里，`0` 恰好代表**重磅**，也就是**最高优先级**。

换句话说：**限流提示伪装成了一条头条。**

如果我不加检查，它会堂而皇之地排在最前面，被当成最重要的新闻推给用户。用户看到的不是「服务暂时不可用」，而是一条言之凿凿的财经快讯。

更扎心的是它的第二个伪装：**时间戳是 `2020-01-01 00:00:00`**。这个不可能的时间，本来是很好认的标志。但我的取数逻辑是「按时间倒序取最新」——于是这条假消息被排到了**末尾**，看起来就像一条正常的历史条目，安静地躺在列表底部。

### 一、坏数据的三张面孔

**面孔一 · 限流提示伪装成一条快讯。** HTTP 200 + 合法 JSON + 字段齐全，内容是「此IP访问受限制，请360分钟后再重新尝试」，`Level` 却是最高优先级的 `0`。

**面孔二 · 报错页伪装成 JSON。** 漏传一个分页参数，后端把 MySQL 的原始报错当正文返回（`Query failed: You have an error in your SQL syntax`），HTTP 照样 200。你的 schema 校验 **100% 通过**。

**面孔三 · 旧数据伪装成「最新」。** 假条目带的是过去的时间戳，在倒序逻辑里被排到末尾，看起来就像一条正常的历史条目。

三张面孔有一个共同点：**它们都不以「报错」的样子出现**。它们穿着正常条目的衣服混进你的结果里。

### 二、为什么「检查状态码」这个习惯必然漏

状态码校验验的是「有没有传回来」，**内容层被整个绕开了**——而限流恰恰只发生在内容层。

原理就一句话：**你验的是传输层，用户信的是内容层。**

服务端把错误信息包进正常条目的字段里，你的 schema 校验当然会通过——这是一个「看起来完美」的失败。而排序还会帮倒忙：假条目带着过去的时间戳倒序排到末尾，如果你只检查「第一条」，反而永远看不到它。

还有一条同源的坑：我遇到过一次 `Unexpected UTF-8 BOM` 的 JSON 解析失败。那不是内容问题，是**协议层的脏字节**——响应头多了一个 UTF-8 BOM。

### 三、破局：给数据加一道「语义哨兵」

在状态码之后再加一层**语义特征校验**，命中哨兵值即判定为异常响应，**显式报错，绝不让它静默流进下游**。

三个哨兵，从便宜到贵：

**哨兵一 · 时间戳不可能区间。** 最新一条的时间早于进程启动时间，或者落在 `2020-01-01` 这类明显不可能的区间 → 判定异常。

**哨兵二 · 正文命中限流词。** 「访问受限制 / 请稍后 / 系统维护 / 频繁访问」→ 判定异常。**这一条最直接，成本最低**，如果只做一个，做它。

**哨兵三 · 关键字段突然全为默认值。** 等级、时间、来源等字段集体塌成同一个默认值 → 判定异常。

这里有两条必须一起说：

- **异常响应要能被单独识别并显式报错。** 静默流进下游 = 把错误当数据用，比直接报错更坏——错数据会被当事实继续加工，越走越远。
- **「没有报错」不等于「数据对」。**

### 四、撞上封禁怎么办：四条铁律

**铁律一 · 不重试。** 封禁时长就写在返回文本里（实测 **360 分钟**），重试等于加刑。而且这类源**翻页会加重限流**——连续翻 **15 页**就触发封禁。所以默认只拉 1 页，翻页之间加节流延迟。

**铁律二 · 降级读缓存。** 接口不可用时读本地快照，并且在输出顶部标注「缓存数据，拉取于 X，N 小时前」。

**铁律三 · 把剩余等待时间告诉用户。** 让用户决定「等」还是「先看缓存」，而不是替他猜。

**铁律四 · 降级不推进消费水位。** 拿缓存冒充实时，会把「其实没读到」的条目误标为已消费。

### 五、增量去重：两种直觉写法都会错

这是另一个独立的问题，但踩的是同一个坑——**单一水位线只能二选一：要么重复消费，要么漏读。**

**直觉一**：用「上次输出**最后一条**」的时间当水位。但接口是**倒序**返回的，最后一条其实是最旧的 → 已消费过的条目被反复吐出来。实测第二次跑，仍返回一模一样的 3 条。

**直觉二**：改用「上次输出**第一条**」的时间当水位（想修正上面那个）→ 被 `--level` / `--keyword` 过滤掉的**同批**条目永远读不到，因为它们的时间戳落在水位之前。

**正解**：存**已消费条目的标识集合**（这里是时间戳集合），拉取时按集合做**差集**。重复和漏读两个问题同时消失。

配套两条：① 只把**实际输出过**的条目记为已消费，被过滤掉的条目下次仍读得到；② 集合设上限（如 500 条）并按时间序裁剪。

### 六、封装值多少：3 轮 A/B 实测

拿快兰斯接口封装成 skill 前后，跑同样的 3 个任务：

| 任务 | 裸做 | 用 skill | 变化 |
|---|---|---|---|
| R1 · 最新重磅快讯 | 122.9s | 98.5s | **-20%** |
| R2 · 某股最近消息 | 594.1s | 85.6s | **-86%** |
| R3 · 过去半年 | 220.4s | 142.8s | **-35%** |
| **合计** | **937.4s** | **326.9s** | **-65%（2.87 倍）** |

最痛的一次是 R2——省下的正是「把接口当谜题破」的那 10 分钟。

**但诚实边界必须一起说**：R2/R3 裸做拿到的**更多**（公告原文、财务、行情）。skill 的价值是更快 + 更少踩坑 + **显式声明数据边界**，**不是覆盖更全**。拿一条快讯流冒充全面尽调，比明说边界更糟。

### 七、数据到手，三问才算合格

**自检一 · 真假。** 哨兵校验过了吗？没过就不要往下走。

**自检二 · 时效。** 最新一条距今多久？这次取数**覆盖了哪一段时间**？（实测该源「最新一条」通常滞后 **30–60 分钟**，采样间隔中位 **1.4 分钟**——不要自己编一个「刚刚更新」。）

**自检三 · 边界。** 这个源**不**覆盖什么？（实测 `Url` 字段 **100 条全空** → 没有原文出处链接；公告原文 / 财报 / 行情 / 研报都不在快讯流里，需另找源核对。）

交付形态固定三块：**结论先行** → **条目列表**（时间 + 等级 + 标题 + 关联个股）→ **数据时效与边界**。

一条底线：降级到缓存时**必须显式声明数据已过时**，不能让用户以为拿到了实时数据。

**说清楚边界，比多拿十条数据更值钱。**
