# 事实核查 SOP · 怀疑者三问

> 三审三校解决的是「写得好不好」，事实核查解决的是「写得对不对」。这是两个完全不同的问题。

## 为什么要独立的事实核查

写作 agent 凭模型知识库写竞品/外部信息，审校 agent 也用同一个知识库校验，错误会在同一个信息茧房里反复传播。

**事实核查员必须**：
- ✅ 用 WebSearch 获取一手信息
- ✅ 对照已下载的官方文档验证
- ❌ **不能依赖模型记忆**

## 怀疑者三问

对每条事实声明，必须问以下三个问题：

### 1. 「这是真的吗？」— 信息本身是否准确

- 产品名称是否拼写正确
- 发布时间是否准确
- 功能描述是否真实存在
- 定价/订阅模式是否正确

### 2. 「来源在哪？」— 能否找到一手来源验证

- 优先：官网 / 官方文档 / changelog
- 次优：官方博客 / 官方 GitHub
- 最后：可信媒体报道（带日期）
- 不可用：模型记忆、用户口述、第三方过时文章

### 3. 「前提成立吗？」— 修正事实后，基于此事实的论点/对比/判断是否仍然成立

**这是最容易被忽略的**。比如「A 和 B 的定价策略很不一样」，即使把 A 的价格改对了，整句的判断（「很不一样」）可能就不成立了。

**事实核查不只是修数字，是质疑论点。**

## 执行流程

### 步骤 1：提取事实声明

单个 agent 逐章扫描 `fragments/`，提取所有事实性声明，分类：
- **本书主题**（如 XX 工具）：对照已下载的官方文档验证
- **竞品/外部引用**（如其他工具/产品）：**必须用 WebSearch 查一手来源**

提取模板：
```markdown
## 事实声明 #N
- 位置：fragments/part3-xxx.html, 第 X 段
- 声明内容：「A 工具不支持并行子任务」
- 类型：竞品功能
- 状态：待核查
```

### 步骤 2：分类核查

| 类别 | 核查方法 | 输出 |
|------|---------|------|
| 本书主题 | 已下载的官方文档 | 正确/不准确/错误/无法验证 |
| 竞品/外部 | **必须 WebSearch 查官网/changelog** | 同上 |
| 时间线/版本号 | 官方 release notes | 同上 |
| 定价/订阅 | 官网 pricing 页（带日期） | 同上 |

### 步骤 3：输出存疑清单

每条标明：
- 原文引用
- 核查结果（正确 / 不准确 / 错误 / 无法验证）
- 一手来源 URL
- 如果是对比/判断类声明：**修正后论点是否仍成立**（最重要！）

```markdown
## 存疑清单

### 声明 #3 ❌ 错误
- 位置：fragments/part5-pricing.html, 第 2 段
- 原文：「A 工具只有按量计费」
- 核查：A 工具 2025 年起推出订阅制，官网 pricing 页明确列出月付/年付
- 一手来源：https://a-tool.com/pricing
- **论点修复**：原对比「A 按量 vs B 订阅」不成立。应改为「A 主推按量 + 提供订阅；B 纯订阅」
- 建议动作：重写第 2 段
```

### 步骤 4：修复

根据清单修复，修复时同样遵循「前提成立吗」原则：
- 数字改了 → 整段对比/论点是否仍成立？
- 时间线改了 → 因果关系是否仍成立？
- 功能描述改了 → 推荐/不推荐是否仍成立？

## 典型易错场景（写作 agent 最容易翻车的地方）

| 场景 | 错误示例 | 正确做法 |
|------|---------|---------|
| 竞品产品形态 | 「XX 只有终端版」→ 实际也有桌面版和 Web 版 | 描述前先看官网产品页 |
| 定价对比 | 「XX 按量计费，YY 订阅制」→ 实际两者都有 | 双方官网 pricing 都查 |
| 功能有无 | 「XX 不支持并行」→ 实际支持 sub-agents | 看 changelog，不靠记忆 |
| 时间线/版本号 | 「XX 是 2025 年发布的」→ 实际是 2024 年 | 看官方 release notes |
| 开源状态 | 「XX 开源」→ 实际只是 npm 分发，代码未开源 | 看 GitHub repo 是否公开 |
| 性能数据 | 「A 比 B 快 10x」→ 实际是特定 benchmark | 看 benchmark 来源 + 条件 |
| 用户量 | 「XX 有 100 万用户」→ 实际是累计下载量 | 区分 DAU/MAU/累计下载 |

## 核查 Checklist（每个项目必跑）

- [ ] 所有竞品的产品形态描述都查了官网
- [ ] 所有定价/订阅信息都查了最新官网 pricing 页（带日期）
- [ ] 所有时间线/版本号都查了 release notes
- [ ] 所有开源/闭源声明都查了 GitHub repo
- [ ] 所有「X 不支持 Y」的判断都查了官方文档
- [ ] 所有 benchmark/性能数据都标注了来源和测试条件
- [ ] 每个存疑项都问过「前提成立吗」

## 一句话心法

> **事实核查不是给错误打补丁，是重新审视整段论述的逻辑链。**
